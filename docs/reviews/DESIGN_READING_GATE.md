## 操作流程

1. 获取 PR 最新分支，在自己的电脑 checkout 最新 head，不用另一人的本地目录或旧附件代替。
2. 执行 `node scripts/review/open-design.mjs`。脚本核对清单、内容哈希和本地 Git head，请求打开阅读页与四张 SVG；文字方案、模块数据和 Wiki 交接均在阅读页中展示。
3. 实际查看这些文件后输入 `已在本机阅读`。脚本只生成绑定 head SHA、内容摘要和文件集合的阅读声明，不调用 GitHub、不自动批准或合并。
4. 使用自己的 GitHub 身份在 Review 正文中粘贴完整声明，审查代码/接口/测试与限制后选择 Approve。不能替另一人签名，不能仅在普通聊天说“同意”。
5. `design-read-confirmations` 检查实时 GitHub review 身份、当前 head、内容哈希及个人本机阅读声明。新的 commit、设计内容变化、撤销审批或 changes requested 使相应门槛失效。
6. 只有必要 CI、该检查和原生分支审批全部满足，且有相应合并授权，才能正常合并。

GitHub 不允许作者批准自己的 PR。若作者是两人之一，其本机阅读声明通过 COMMENTED review 记录，另一个人的审批仍必须有效，并且仍需满足仓库原生“两次外部批准”的门槛；作者声明不算平台审批、不免除任何检查。当前交付 PR 作者为 zemeng5208，goo122 和 Potatos498 均可正常批准。

## 禁止绕过

- 禁止 `gh pr merge --admin`、force merge、强推、直接推 main、跳过/改绿检查、删除保护或改成自审后合并。
- 禁止开启绕过当前门槛的自动合并，冒用账号、复制另一人的声明或修改清单伪装阅读。
- 管理员也必须遵守保护；CODEOWNERS 单独只要求任意一个 owner，不能当作两人门槛。
- 检查因等待确认而失败是有意阻止合并，不通过放宽规则“修复”。

## 技术验证范围

仓库可以核实账号身份、审批状态、提交版本和个人阅读声明；**无法独立证明远端电脑的真实屏幕、网页可见或人的理解**。启动请求不是阅读证据，阅读声明属于实名自证。`--verify-only` 不打开页面、不生成阅读声明，不能满足门槛。

本地检查和原生分支保护互相补充，不把仓库可修改的 workflow 宣称为不可篡改安全边界。修改工作流、CODEOWNERS 或门槛脚本本身同样需要审批。持有仓库管理权限的人理论上能修改保护设置；当前政策禁止这样绕过，不能宣称 GitHub 使管理员永久失去设置权限。

远端实际设置与状态以 API 读回和当前 PR checks 为准；文档写入不等于保护已启用。发布镜像与代码合并分别记录，预览镜像标签不代表 main 已合并或华为云验收通过。
