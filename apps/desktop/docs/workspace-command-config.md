# Desktop workspace command configuration

The Competition Desktop keeps the selected workspace in the existing encrypted `coding-workspace.json` version 1 record. Optional encrypted fields hold a user-selected Node executable, one workspace-relative JavaScript file for syntax checking, and a fixed npm CLI file outside the workspace. Older version 1 records remain readable and retain their read and patch abilities. A new selection revokes the current session grant; the tool catalog is rebound after a Desktop restart.

Trusted Main injects `selectNodeExecutable()`, `selectCheckFile(workspaceRoot)`, and `createCommandRecipeTool(options)` into `createWorkspaceConfigHost`. A fallback `selectNpmCli()` is needed only when the fixed `node_modules/npm/bin/npm-cli.js` file cannot be resolved from the selected Node installation. The callbacks use native file dialogs and return absolute paths to Main only. Renderer invokes `coding.selectNode`, `coding.selectCheckFile`, and `coding.selectNpmCli` without path arguments. The host requires the Node executable and npm CLI to be regular files outside the writable workspace and the selected `.js`, `.mjs`, or `.cjs` file to be a regular file inside it. The recipe helper verifies fixed canonical paths again. The model sees empty input objects and cannot choose an executable, path, arguments, or working directory.

`workspace.node_check` wraps the public `workspace.run_allowed_command` recipe with fixed `node --check` arguments. It is available only after this session's cloud export and separate command permission are enabled; workspace write permission remains independent. Runtime Policy and ToolGateway still gate each execution. Only `{recipeId, exitCode, passed}` is projected to AgentArts; raw stdout, stderr, source excerpts, and paths remain local.

Project `npm run build` and `npm run test` are registered as fixed `workspace.npm_build` and `workspace.npm_test` wrappers only when trusted Main supplies an already prepared helper executable outside the workspace, a fixed npm CLI is available, and the recipe factory returns `diagnostics.projectScriptsExposed === true` with the matching recipes. Main now checks the fixed `userData/native-tools/workspace-command/WindowsJobProcessHost.exe` location and injects it only when present. Missing artifacts, npm configuration, scripts or dependencies keep these tools unavailable; the app does not build or install them automatically. Availability also requires explicit `cloudExportAllowed`, `commandAllowed`, and separate session-only `projectCodeAllowed`; revocation invalidates task bindings. Raw process output remains local and only recipe ID, exit code, and pass status can be projected. Project scripts execute workspace code and are not a system sandbox. The assembly owner must verify the helper's complete artifact batch and provenance before use; an existing executable alone does not prove process-tree termination or npm acceptance.

The focused tests cover legacy configuration, encrypted option persistence, an actual fixed Node syntax check, separate write and command permissions, redacted export, revocation, invalid file selection, and a Fake recipe factory for project-script readiness and consent. They do not establish real npm execution, Electron dialog, or AgentArts acceptance.

## Local results and per-read PUBLIC export

The existing session field `cloudExportAllowed` remains in the version 1 configuration/UI contract for compatibility. It enables the selected local tool scope; it does not establish that every file in that scope is PUBLIC. Local `workspace.read_text` results retain their original content and raw-byte digest. Without an exact native-confirmed export provider, their Competition projection returns `UNSUPPORTED_CAPABILITY` rather than source text.

The narrowed `coding-local-result-redacted-v2` policy returns only list/preview/stage/apply status. Names, paths, preview text, staged paths, backup references and private file digests stay local. Git diff checking, Node checks and project commands return only `{recipeId, exitCode, passed}`; raw stdout/stderr remain local. Cached continuations using the previous broader export policy are not compatible with this policy change.

PUBLIC reads consume `@personal-agent/mcp.createWorkspaceReferenceExport`, with the two-phase `workspace-reference-3.0.0` public contract from PR #269, pinned to source commit `3b1b8a490fe5a73f754aca49ac2190e2fb4eb312`. Trusted Main injects that factory as `createWorkspaceReferenceExport` and the synchronous `readWorkspaceExportPreflight(input)` and `readWorkspaceExportAuthorization(input)` callbacks into `createWorkspaceConfigHost`. They implement the public `WorkspaceReferenceExportOptions` readers and reuse the public native authorization types; the host does not copy those DTOs. The preflight callback receives the public query plus complete arguments, and the confirmed callback receives the public query plus exact content digest and byte length. They must read native PUBLIC grants rather than create a grant or prompt a Renderer. No new package dependency, durable store, or execution loop is introduced in this host. Missing ports reject export while the original local read result remains unchanged.

The Main-only `readWorkspaceExportConfigurationRef()` returns the current session/root/generation reference, including when no Node executable was selected. Both candidate methods accept exactly `{taskId, proposalId, path, configurationRef}`. `readWorkspaceExportPreflightCandidate(query)` returns frozen target metadata from the original persisted proposal: the same query, original `runId`, `toolName`, `toolVersion`, complete `arguments` (including `maxBytes`), and the original task `deadline`. It supplies no SHA, bytes or execution receipt and never reads a file. `readWorkspaceExportCandidate(query)` additionally requires the original confirmed execution and returns `contentDigest` and `byteLength`; it contains no source body. `readConfirmedWorkspaceExport({...query, arguments, contentDigest})` consumes the public `PublicReferenceReadQuery` plus digest and returns only `{runId, result}` using the original `WorkspaceReadResult` checkpoint. The confirmed authorization callback receives those same complete arguments plus `byteLength`. These methods must remain in trusted Main; their IDs, paths, arguments, SHA and original result must not enter Renderer snapshots or cloud messages.

The confirmed reader checks the original Competition pending proposal's `competition-tool-${taskId}-${step}` mapping, exact input/scope digest through the Runtime public matcher, tool/version/protocol, Policy allow, confirmed/executed/finished record, same-task Evidence, original result checkpoint, UTF-8 byte count/SHA, task cancellation/deadline/profile, and the current selected root/consent generation. Preflight pins only the original proposal/run/deadline; confirmation separately pins the original result, without replacing execution records or granting permission. Historical receipts without an original mapping are unavailable; matching arguments alone cannot identify a run. Changed `maxBytes`, proposal, run, result, task, Evidence or grant is refused. Native expiry must not exceed the original task deadline. Revocation, renewed consent, changing application/selection and close discard the helper and original pins; final Competition I/O must still run its original export guard.

`workspace-reference-3.0.0` projects `{source:'approved-workspace-reference', content, byteLength, contentDigest, truncated:false, readConfirmed:true}` only after original confirmation and exact PUBLIC content authorization. The preflight permission declares PUBLIC sensitivity, an explicit permitted purpose and a bounded `maxExportBytes`; it grants neither tool execution nor content export by itself. The helper refuses oversized content rather than silently truncating or inventing a length. Paths, native grant IDs, run IDs and raw Evidence remain local. The shared Runtime must persist its original parsed pending proposal and step before calling `accepts({...originalProposal, phase:'preflight'})`, run the original Policy/Gateway read, await P8's native exact-content confirmation, and then project. Immediately before real cloud I/O and during continuation replay it must call `accepts({...originalProposal, phase:'final', projection:originalContinuation.result})`. Missing phases or final projections are denied; neither preflight nor a cached successful projection substitutes for the final fresh check. A rejected projection must preserve the original confirmed result and pending proposal for the Runtime's existing recovery path; recovery reprojects that confirmed run without executing a second read or reopening a terminal task.

A Renderer checkbox, a caller-supplied result, cached content or the workspace binding getter cannot provide PUBLIC authority. MCP's other reference helper accepts an actual `McpReadResult` with its MCP provenance; coding results keep their workspace provider identity. The native dialog, grant storage and revocation belong to trusted Main. Prepared cases use explicit unit receipt fixtures and the actual public export factory, with no claim of real Runtime/Policy/Evidence or native/cloud acceptance. They are reserved for the final unified local suite; no new stage test or live cloud verification is claimed.

## Trusted workspace binding for local read-only services

`createWorkspaceConfigHost` exposes `readWorkspaceBinding()` and `isWorkspaceBindingCurrent(binding)` to trusted Main only. The getter returns a frozen `{rootPath, nodeExecutable, bindingId}` or `undefined`; these private absolute paths and the binding ID must not enter Renderer state, logs, MCP result payloads, or cloud exports. It reuses the existing version 1 encrypted settings and the current consent generation, with no additional store or grant.

The getter requires an active host, explicit current-session workspace read consent (`cloudExportAllowed`), the same bound root identity, and the same Node selection and file identity. Node must remain a canonical regular file outside the workspace; device/inode, birth time, size, modification time and change time are checked against assembly. This checks the configured file identity, not a publisher signature or atomic process-launch guarantee. A missing Node binding disables this port without removing existing read tools.

Revocation, renewed authorization, selection changes and close invalidate old binding IDs. Selecting a different root or Node cannot silently replace the already assembled binding: reassembly and new explicit consent are required. The validator accepts exactly three own string data fields and verifies all three against a fresh getter; missing/extra fields and accessors are rejected. The getter neither starts a server nor authorizes a tool call.

Main supplies a current binding to a local service factory and checks it again before each operation. Main must stop/cancel that service on revocation, changed settings or close, and reject results from an outdated binding; the validator itself does not cancel a process or authorize file-content export. MCP composition, read-only enforcement, Runtime Policy and lifecycle hooks remain the assembly owner's responsibility. Focused binding cases verify these port semantics with synthetic metadata fixtures; no MCP process or selected Node fixture is executed.
