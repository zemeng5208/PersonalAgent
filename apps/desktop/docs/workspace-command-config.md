# Desktop workspace command configuration

The Competition Desktop keeps the selected workspace in the existing encrypted `coding-workspace.json` version 1 record. Optional encrypted fields hold a user-selected Node executable, one workspace-relative JavaScript file for syntax checking, and a fixed npm CLI file outside the workspace. Older version 1 records remain readable and retain their read and patch abilities. A new selection revokes the current session grant; the tool catalog is rebound after a Desktop restart.

Trusted Main injects `selectNodeExecutable()`, `selectCheckFile(workspaceRoot)`, and `createCommandRecipeTool(options)` into `createWorkspaceConfigHost`. A fallback `selectNpmCli()` is needed only when the fixed `node_modules/npm/bin/npm-cli.js` file cannot be resolved from the selected Node installation. The callbacks use native file dialogs and return absolute paths to Main only. Renderer invokes `coding.selectNode`, `coding.selectCheckFile`, and `coding.selectNpmCli` without path arguments. The host requires the Node executable and npm CLI to be regular files outside the writable workspace and the selected `.js`, `.mjs`, or `.cjs` file to be a regular file inside it. The recipe helper verifies fixed canonical paths again. The model sees empty input objects and cannot choose an executable, path, arguments, or working directory.

`workspace.node_check` wraps the public `workspace.run_allowed_command` recipe with fixed `node --check` arguments. It is available only after this session's cloud export and separate command permission are enabled; workspace write permission remains independent. Runtime Policy and ToolGateway still gate each execution. Only `{recipeId, exitCode, passed}` is projected to AgentArts; raw stdout, stderr, source excerpts, and paths remain local.

Project `npm run build` and `npm run test` are registered as fixed `workspace.npm_build` and `workspace.npm_test` wrappers only when trusted Main supplies an already prepared helper executable outside the workspace, a fixed npm CLI is available, and the recipe factory returns `diagnostics.projectScriptsExposed === true` with the matching recipes. No helper is injected in the current production Main composition, so these tools remain unavailable there. Availability also requires explicit `cloudExportAllowed`, `commandAllowed`, and separate session-only `projectCodeAllowed`; revocation invalidates task bindings. Raw process output remains local and only recipe ID, exit code, and pass status can be projected. Project scripts execute workspace code and are not a system sandbox. Main must not inject the helper path until its native build, packaging, and process tree review are complete.

The focused tests cover legacy configuration, encrypted option persistence, an actual fixed Node syntax check, separate write and command permissions, redacted export, revocation, invalid file selection, and a Fake recipe factory for project-script readiness and consent. They do not establish real npm execution, Electron dialog, or AgentArts acceptance.

## Trusted workspace binding for local read-only services

`createWorkspaceConfigHost` exposes `readWorkspaceBinding()` and `isWorkspaceBindingCurrent(binding)` to trusted Main only. The getter returns a frozen `{rootPath, nodeExecutable, bindingId}` or `undefined`; these private absolute paths and the binding ID must not enter Renderer state, logs, MCP result payloads, or cloud exports. It reuses the existing version 1 encrypted settings and the current consent generation, with no additional store or grant.

The getter requires an active host, explicit current-session workspace read consent (`cloudExportAllowed`), the same bound root identity, and the same Node selection and file identity. Node must remain a canonical regular file outside the workspace; device/inode, birth time, size, modification time and change time are checked against assembly. This checks the configured file identity, not a publisher signature or atomic process-launch guarantee. A missing Node binding disables this port without removing existing read tools.

Revocation, renewed authorization, selection changes and close invalidate old binding IDs. Selecting a different root or Node cannot silently replace the already assembled binding: reassembly and new explicit consent are required. The validator accepts exactly three own string data fields and verifies all three against a fresh getter; missing/extra fields and accessors are rejected. The getter neither starts a server nor authorizes a tool call.

Main supplies a current binding to a local service factory and checks it again before each operation. Main must stop/cancel that service on revocation, changed settings or close, and reject results from an outdated binding; the validator itself does not cancel a process or authorize file-content export. MCP composition, read-only enforcement, Runtime Policy and lifecycle hooks remain the assembly owner's responsibility. Focused binding cases verify these port semantics with synthetic metadata fixtures; no MCP process or selected Node fixture is executed.
